# ManyLangs 성별 검수기 제작을 위한 인계 문서 (v2)

이 문서는 conversation 파이프라인 작업 중 논의된 성별(문법적 성) 검수
관련 내용을 정리한 것이다. 별도 대화에서 이 문서를 기반으로 실제
검수 스크립트/프롬프트를 만든다.

v2 변경사항: 3장(검수 범위) 세분화, 4장 언어 간 하드룰 추가,
6~7장을 설정(config) 기반 2-스크립트(검수기/교체기) 구조로 재작성.

━━━━━━━━━━━━━━━━━━
1. 배경 — 왜 필요한가
━━━━━━━━━━━━━━━━━━

conversation 회화 교재는 화자 A(여성)/B(남성)가 세트 안에서 고정된
구조다 (홀수 줄=A=여성, 짝수 줄=B=남성). GENERATOR_XX.md가 원문을
만들 때 이 규칙을 지키게 돼 있지만, 실측 결과 **DeepSeek이 이 규칙을
안정적으로 못 지킨다**는 게 확인됐다.

실측 사례 (es, batch 001, 성별 표시 언어인 스페인어 target):
- 10세트 중 4세트(40%)에서 성별 오류 발견
- 세트 002: B(남성) 줄에 여성 이름(Elena), 여성형 어미(Encantada)가
  섞여 나옴 / A(여성) 줄에 남성 호칭(el señor)이 나옴
- 세트 003: 같은 인물(A)을 한 세트 안에서 Diego(남성 이름)→Marta
  (여성 이름)로 다르게 호칭
- 세트 007: B에게 "la señora"(여성 호칭)로 질문하는 등 성별 혼선

별도 세션에서 수동 검수한 프랑스어 SRT 사례도 있음 (아래 4장 참고).
언어 학습 콘텐츠에서 이런 오류는 일반 오역보다 훨씬 심각하다 —
학습자가 지금 배우려는 문법 항목 자체를 틀리게 가르치는 것이기 때문.

규모: 9개 목표언어 × 60배치 × 10세트 × 6줄 × 8개 번역 컬럼 ≈ 26만 줄.
검수 없이는 이 정도 규모에서 수천 줄 단위로 성별 오류가 남을 것으로
추정됨.

2. 성별 표시가 필요한 언어 (신중 검수 대상)
━━━━━━━━━━━━━━━━━━

**핵심 5개** — 서술적 형용사·과거분사·직업명이 화자 성별에 따라
어미가 바뀌는 언어:
- es (스페인어)
- fr (프랑스어)
- pt (포르투갈어, pt-BR 브라질 표준)
- it (이탈리아어)
- ru (러시아어, 과거시제 동사가 주체 성별로 어미 변화)

**부분 해당 1개**:

**해당 없음** (문법적 성별 자체가 없음):
- kr, en, zh, jp — 검수 대상에서 제외하되, "이 줄은 몇 번째라 여성/

3. 검수가 필요한 콘텐츠 범위
━━━━━━━━━━━━━━━━━━

**3-A. conversation (지금 만드는 회화 교재)**: 대상. A/B가 세트
안에서 고정된 캐릭터라 "정답 성별"이 줄 번호로 이미 확정된다.
- KR-target, EN-target 등 기존 책들의 es/fr/pt/ru/it 번역 컬럼도
  포함 (target이 성별 없는 언어일 때, 번역기가 문맥만으로 매 줄
  성별을 새로 추론해야 해서 오히려 이쪽이 더 취약할 수 있음).

**3-B. 문법(grammar_explanation/example) / 이디엄(idiom) / 보카
(vocabulary) / situational(상황 묘사)**: 대상이지만 conversation과
검수 로직이 다르다. 이 4종은 화자가 1명(내레이터)이고 세트를
넘나드는 고정 캐릭터 정체성이 없어서, "이 줄은 무조건 여성/남성"
이라는 줄 번호 기반 정답표는 없다. 대신 아래 기준으로 분기한다:

```
원문(en/kr 등)에 성별이 이미 명시돼 있는가?
  YES (예: "she is a doctor", 성별이 명백한 이름/대명사/호칭)
    → 성별표시 언어(es/fr/pt/it/ru/de) 번역이 그 성별과
      일치하는지 대조. 불일치 = 오류 (conversation과 동급 심각도)
  NO (원문이 성별 중립)
    → 번역기가 임의로 정한 성별을 문제 삼지 않되,
      같은 문단/문장 안에서 그 성별 표지가 도중에
      안 바뀌는지(내적 일관성)만 확인
```

(참고: 성우 목소리 성별과 텍스트의 문법적 성별은 완전히 별개이며
일치시켜야 할 이유가 없음 — 이미 정정된 논점.)

4. 검증된 판정 방법론 (다른 세션에서 실전 검증됨)
━━━━━━━━━━━━━━━━━━

화자 고정 (conversation): **1·3·5번 줄 = A = 여성,
2·4·6번 줄 = B = 남성**.

판정은 반드시 아래 3분류로 나눠서 확인한다 (단순히 "이 줄 화자가
남자냐 여자냐"만 보면 안 됨):

- **본인 지칭**: 화자가 자기 자신을 묘사 → 현재 줄 화자의 성별 적용
- **상대방 지칭**: 화자가 대화 상대를 묘사 → 상대방(반대쪽 A/B)의
  성별 적용 (예: B가 A에게 "너 피곤하니?"라고 물으면 A는 여성이므로
  여성형 사용)
- **제3자 지칭**: 대화에 A/B 외 인물이 언급되면 그 인물의 실제
  성별 적용 (문맥으로 확정, 확정 안 되면 임의로 정하지 않음)

과거분사·형용사·직업명·대명사·호칭 등 성별이 드러나는 모든 요소에
동일하게 적용. 러시아어처럼 화자 성별이 과거형에 나타나는 언어도
"행동의 실제 주체가 누구인가" 기준으로 확인.

**절대 원칙**: 성별이 드러나지 않음 = 허용 (모든 문장에 성별 표지를
강제할 필요 없음) / 성별이 드러났는데 설정과 불일치 = 필수 수정.
심각도는 문법 오류와 동급 최우선 등급.

**하드룰 — 같은 블록 내 성별언어 간 상호 일치 (신규)**: 같은 줄
안에서 es/fr/pt/it/ru/de 중 성별이 드러나는 언어들은 서로 반드시
같은 성별 형식을 유지해야 한다. 하나라도 다르면 무조건 오류로
판정한다 (예: es는 여성형, fr은 남성형이면 최소 하나는 틀린 것).
이 체크는 API 판단이 아니라 코드로 직접 비교하는 구조적 검증이라
신뢰도가 가장 높다.

가족관계 호칭(오빠/형/누나/언니 등)도 발화자가 A인지 B인지에 따라
판단 (단순 brother/sister 직역 금지). 직업 성별도 마찬가지
(예: B=남성 간호사 → 러시아어 медбрат, 여성이면 медсестра).

존댓말/반말 및 격식 일관성(ты/Вы, tu/vous, tu/Lei, du/Sie 등)이
세트 안에서 섞이는지도 같은 항목으로 확인.

프랑스어 실전 사례 (다른 세션, 수동 검수):
```
3번 A(여): je suis un peu fatigué → je suis un peu fatiguée (수정)
4번 B(남)가 A(여)에게: Pourquoi tu es fatigué ? → Pourquoi tu es fatiguée ? (수정)
```
→ 3번은 본인 지칭(A 자신), 4번은 상대방 지칭(B가 A를 가리킴).
둘 다 실제 지칭 대상이 A(여성)라서 여성형이 정답.

━━━━━━━━━━━━━━━━━━
5. 신뢰도 추정 (검수기 설계 시 반영)
━━━━━━━━━━━━━━━━━━

네 가지 검수 방식은 신뢰도가 다르다:

- **본인/상대방 지칭**: 줄 번호로 정답이 이미 확정돼 있어서, API는
  "판단"이 아니라 "확인"만 하면 됨 → 신뢰도 높음 (90%대 중후반 추정)
- **언어 간 상호 일치 하드룰**: API 판단력이 아니라 코드로 직접
  비교하는 구조적 검증이라 **신뢰도가 가장 높음** (거의 100%에 가까움)
- **원문 성별 명시 → 번역 대조** (3-B 콘텐츠): 원문이 이미 정답을
  주므로 구조적 대조에 가까움 → 신뢰도 높음
- **제3자 지칭 / 원문 중립 시 내적 일관성**: 문맥 추론이 필요해서
  더 어려움 → 신뢰도 상대적으로 낮음 (80%대 초반으로 보수적 추정)

전략: 구조적 확인·비교(본인/상대방, 언어 간 하드룰, 원문 명시 대조)를
메인으로 쓰고, 제3자 지칭·순수 문맥 판단만 API 판단에 의존하는
가장 약한 고리로 취급. 이 조합이면 완전 자동화로 0%는 못 만들어도
실사용 가능한 수준(잔존 오류율 1% 이하)까지는 현실적으로 도달 가능.
다만 26만 줄 규모에서 완전 무인 자동화는 위험하므로, 신뢰도 낮은
항목이 몰리는 배치를 골라 표본을 사람이 마지막으로 확인하는 안전
장치를 권장.

6. 현재 파이프라인 구조 (검수기가 연동해야 할 대상)
━━━━━━━━━━━━━━━━━━

경로: `/Users/junghasuk/Desktop/ManyLangs/web/firebase/conversation generator/`

```
$PROJ/
├── languages.py              — 8개 번역 언어 정의 (en/es/fr/pt/kr/jp/zh/ru)
├── text_parser.py            — GENERATOR/TRANSLATOR 텍스트 출력 파서
├── promote_draft.py          — draft.json → compact.json 승격
├── deepseek_generate.py      — target/translate 자동 생성 (텍스트 출력 방식)
├── merge.py                  — target+8언어 compact.json → 최종 runtime.json
├── review.py / conversation_checker.py — 기존 검수 스크립트 (수정안 딕셔너리 방식)
├── prompts/
│   ├── GENERATOR_{KR,ES,FR,DE,IT,PT,RU,ZH,JP}.md
│   ├── TRANSLATOR_{EN,ES,FR,PT,KR,JP,ZH,RU}.md
│   ├── REVIEW_PROMPT.md      — 수정안 출력 (TITLE_REPLACEMENTS/REPLACEMENTS 딕셔너리)
│   └── EVAL_PROMPT.md        — 문법/자연스러움 점수표 출력 (수정 없음, 채점만)
├── data_es/, data_fr/, data_pt/, data_zh/, data_jp/, data_ru/  — 목표언어별 책
│   └── {batch}/
│       ├── {batch}-target.draft.json / .compact.json
│       ├── {batch}-{lang}.draft.json / .compact.json (번역언어별 ×7)
│       └── conversation_{batch}.runtime.json  — 최종 8개 언어 통합본
```

각 `conversation_{batch}.runtime.json`은 `title`/`blocks[].lines[].sentences`
아래 target+8개 언어 전부를 갖고 있어 **언어 간 교차검증에 바로 쓸 수 있음**.
화자(A/B)는 `blocks[].lines[].speaker` 필드로 명시돼 있거나, 세트 내
줄 인덱스(0,2,4=A / 1,3,5=B)로 암묵 결정됨 (스키마는 merge.py 참고).

기존 REVIEW_PROMPT.md/EVAL_PROMPT.md는 문법/자연스러움 전반을 다루는
범용 검수이고, 이번에 만들 성별 검수기는 그중 성별 항목만 떼어내
더 좁고 깊게, 그리고 가능하면 API 호출 스크립트로 자동화하는 것이 목표.

7. 앞으로 만들 것 (다른 대화에서 진행) — 설정 기반 2-스크립트 구조
━━━━━━━━━━━━━━━━━━

→ 교체기(fix)** 흐름으로 확정. 사람이 최종 반영 전에 검토할 수 있는
체크포인트를 리뷰 파일 단계에 둔다.

  줄 인덱스 0,2,4=A / 1,3,5=B)
- `config.json`으로 저장 — 폴더/배치마다 스키마가 조금씩 달라도

**[1] `gender_audit.py --config config.json` (검수기, 읽기 전용)**

  line, lang, 현재값, 제안값, 근거(본인/상대방/제3자/교차검증/원문대조),
  confidence}`

**[2] (선택) 사람 검토**
